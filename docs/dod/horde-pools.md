# DoD: Horde pools — full-size hordes, a castle-territory switch for hordes, and a shared faction pool library

**Size:** M. Three small-to-medium changes to the apocalypse family (HordeMarch, Infestation, Apocalypse) and to pool resolution, with one new data file (`BepInEx/config/Nyarlathotep/pools.json`), one new chat command group (`.nyar pool`), two schema additions in events.json (`action.allowTerritory` on the three horde types; `min`/`max` on unit pool entries) and one cfg default change (`[Limits] MaxTrackedUnits` 150 → 500). L test: no new external dependency, no wire change, no new pillar; it touches Logic (Limits, Precedence, Apocalypse, ApocalypseHost, Pools, Validation, CommandArgs, EventAdmin, Messages, Paths), Services (SpawnTracker's ledger call, ApocalypseAction, a pool-library loader), Commands and the release surfaces.
**Planned:** interactively; the owner settled the four decisions on 2026-10-24 (design §9 D65, Epic A49). The Halloween track's light process applies (design §9 D34): one review round, two at most; Codex once on the child's diff before release; a vrclient scenario as the in-game evidence; the owner checks only look and feel.
**Request:** the owner, 2026-10-24: "1. Can we ensure that in horde mode, they are capable of spawning up to the maximum number of units of the event at once, Not limited to only 20 or 30 2. please be sure that, in horde mode, the setting that enables the horde to go onto castle territories is present as a configurable modifier, and also that it should be disabled by default. 3. Please ensure that we already have pools of units that are established, similar to templates, and can be called from and attached to spawning events. This is separate from the event itself. The event itself has its own configurations and can, of course, have specific units designated with each wave or in association with a horde. Otherwise, we need to have pools of faction resources available that can be called upon and linked into events so that it can utilize a random count of that pool of units. There should be separate pools for bosses of each faction versus the units of each faction."

**North Star:** an admin on a default cfg gets a horde of the size the event asks for (up to 500), keeps castles safe from hordes unless they switch `allowTerritory` on per event, and links any event to shared faction unit and boss pools with a random count, without copying unit lists between events; shipped in the next minor release; finished when D1-D18 have evidence (D13 may wait on the owner).

## Purpose & typical use
The owner ran the horde march on the G-Portal server at default caps and got 20 skeletons where the template asks for 200 (C1). They want hordes kept out of castles unless they choose otherwise (C2), and they want the faction unit lists the mod already knows to be shared building blocks instead of copied into each event (C3). 1.1: server admins building or running horde and wave events. 1.2: an event that rises at full size and pulls its units from shared pools like `undead-units` and `militia-bosses`. 1.3: it extends the apocalypse family's caps and territory rules and wave-variety's pools; the event's own `pools` keep working and win over the library.

## Use cases
### Typical
An admin on a fresh install uses `undead-horde-march`: 200 undead and the Bishop of Death rise and march. Players at home in their castle are left alone. For a weekend event the admin writes a SpawnWaves event whose waves name `pool:legion-units:8-14` and a final boss roll from `legion-bosses`, without listing a single prefab; `.nyar pool info legion-units` shows what can appear. For a raid night they copy the horde template and set `action.allowTerritory true`.

### Minimal stretch
- 8.1 No pools.json yet: the first boot writes the 17 seeded pools; an event naming no library pool behaves exactly as in 0.14.0; a horde smaller than 20 behaves as before (D5, D6, D1).
- 8.2 Used once: a single horde event, started once, with the switch at its default; the library is read once at boot (D3, D5).

### Maximal stretch
- 9.1 Volume: a 500-unit horde on a 500 cfg; 64 library pools of 30 members; an event with 8 own pools and library references; every entry at max 500 still bounded by the horde's 10-500 and the tracked cap (D1, D5, D7).
- 9.2 Abuse: an admin edits pools.json to name a denied or unknown unit — the file loads nothing and says why; a library pool whose members span two allied groups, or hold a unit in no group, loads with one boot warning "[nyar] pool <name> mixes groups: <groups>" and `.nyar pool info` shows the same warning, as an event's own pools are not refused for mixing today (D5, D8, S-10). Non-admins cannot read or reload (D8).
- 9.3 Repeated use: reloads in a row never change a running event's draw; a reload that breaks events names them (D6, D8).

## Business rules
1. **Which cap holds a horde** (D1): HordeMarch, Infestation and Apocalypse hordes and rises are held by the free MaxTrackedUnits slots only; SpawnWaves stays held by MaxUnitsPerWave then MaxTrackedUnits. One horde at the cap fills every slot, so other events' spawns are skipped by MaxTrackedUnits while it lives (S-11); only one apocalypse-type event runs at a time.
2. **Territory** (D3, D4): one per-event switch, `action.allowTerritory`, on the three horde types, default false; off covers targeting, every move, every spawn and the march's end; on lifts all of them. The game's own AI chasing a player into a castle after combat starts is the game's, not the mod's (S-6).
3. **Pool names** (D6): own pools first, then the library; unknown in both refuses the event.
4. **Precedence** (4.4): General.Enabled and the pillar switches still stop everything; the kill switch and purge are unchanged; `allowTerritory` true on an event beats the castle refuge for that event only; an event's own pool beats a library pool of the same name; an invalid pools.json beats nothing (no library pools, events naming them invalid).
5. **"Every" sets** (4.5): every horde spawn path goes through Apocalypse.Queue → SpawnLedger.Request (grep: the only ledger caller in Logic/Apocalypse.cs); every territory decision of the family goes through one of five sites: IApocalypseGame.IsClaimed (ApocalypseHost.cs lines 588-637, the roam and infest moves), the march step and arrival, spawn placement (Apocalypse.Queue's place), the hunt layer's candidate filter (Services/HuntAction.cs Candidate, HuntRule at Logic/Spawning.cs:939) for units carrying a HuntTag from Apocalypse.Queue, and the unit watch's landing rule (Logic/UnitWatch.cs Context, which reads the definition's AllowTerritory); all five read the event's switch; every pool lookup goes through the one resolution used by Pools, Validation.FamilyHead and FactionGroups.
- whole: none — the library and the caps hold no parts that add up to a total anyone checks
- siblings: HordeMarch, Infestation, Apocalypse

A mistake here can spawn more units than intended (still held by MaxTrackedUnits and the spawn-per-tick budget) or let a horde into a castle; nothing writes a prefab or a save.
- **Contracts (5.3):** pools.json's schema; the events.json additions; the `.nyar pool` replies; the cfg default; the wire unchanged (D9).

### External — dependencies and their failure behaviour
- **6.1 The game:** castle territory blocks (TerritoryMap, proven since event-spawns D17) and the spawn system (proven to 500 units by undead-hordes D25-D26).
- **6.2 Failure:** a territory map that cannot be built fails closed (every point claimed) when the switch is off, as today, and is not needed when on; a pools.json read failure is D5's path.
- **6.3 Test mode:** vrclient on the dev server (D12); the unit tests use fakes for the world and the file store.

## Design
### Data
| Artifact | Where | Owner | Kept | Deleted |
|---|---|---|---|---|
| pools.json | BepInEx/config/Nyarlathotep/ | the operator (seeded once by the mod) | until edited | by the operator; 0.14.0 ignores it (D14) |
| events.json additions | the same folder | the operator | as events.json | as events.json |
| the MaxTrackedUnits default | kdpen.Nyarlathotep.cfg | the operator | a written value stays | by the operator |
| resolved pools of a running event | memory | the event runtime | until the event ends | at its end |
| session log copies | %TEMP%\nyar-hp-logs | Claude | the session | deleted after the release (D16) |

Migration (3.4): none for events.json; a cfg that already holds `MaxTrackedUnits = 150` keeps it (BepInEx writes a default only when the key is missing), so existing servers must raise it by hand; the READMEs and the start reply's cut line say so (D15, D1).

### States
- **7.1** Empty: no pools.json → seeded; an empty or invalid file → no library, one line, health entry (D5). First run of a horde: full size (D1). Error: D5's line; a horde start on claimed ground refused (D3).
- **7.2** Concurrent use: the library is read on the scheduler thread only (boot, reload); a running event holds its own resolved copy; two events naming one pool draw independently.
- **7.3** Castle map: a run's territory map is built at its start and on resume, as in 0.14.0; a castle claimed later counts once the run's map is rebuilt (S-12). Cancel and re-entry: a reload mid-event changes later starts only; a restart re-resolves from the current file at resume; stopping an event drops its copy.

### Permissions
- **2.1** Admins: `.nyar pool` and `.nyar event set` (VCF adminOnly). Players: nothing new. The operator: pools.json and the cfg.
- **2.2** A non-admin calling `.nyar pool` gets the framework's refusal (D8).
- **2.3** Ownership: the library belongs to the server; an event's own pools to that event.

### UX
- **11.1** Discovery: `.nyar pool list`, the READMEs and changelogs (D8, D15).
- **11.2** Feedback: plain chat lines; reload names broken events; the start reply names the cap that cut a horde (D1, D8).
- **11.3** Accessibility: plain text within Wire.MaxBytes, no rich text, no "< >".
- **11.4** Activation: commands by admins; the switch per event; the seed once at the first boot without a file.
- **11.5** Design bar: the owner judges the horde's size and feel, the castle switch and the pools' usefulness (D13); chat replies follow the project's plain style.

## Security
- **10.1** Authorization: the new commands are adminOnly; pools.json lives in the operator's config folder; Persistence's file-write fence gains exactly pools.json, pools.json.bak, pools.json.tmp and pools.json.corrupt (DataFile.Pools; D5).
- **10.2** Injection: pool and unit names are checked against the name rule and the unit catalog before use; nothing reaches a shell or a query (D5, D7).
- **10.3** Secrets: none added (D17).
- **10.4** Personal data: none stored; replies and log lines carry names of pools and events only (D11).

## Failure & observability
- **12.1** The admin sees: the start reply's cut line, reload's invalid list, the boot line for pools.json; next: edit the file or the cfg (D1, D5, D8).
- **12.2** Logged: "[nyar] pools.json not loaded: <reason>", "[nyar] pools: <n> loaded (<k> seeded)" at boot, the existing cut and hunt-tally lines (D5, D12).
- **12.3** Knowing it is broken: the "pools unknown" health entry in `.nyar status`, -LogCheck after each session, the vrclient scenario (D5, D16, D12).
- **12.4** Failing cases: every test and cmd item names its fails-when and has a ControlCases row (D10); each new test's planted fault is run in its step and logged.

## Performance
- **13.1** Budget: the existing tick budget (under 5 ms average a window). The undead-hordes load ladder measured 500 units: the mod's tick 1.2 ms, the server about 19 fps with a player among them (docs/features/UNDEAD_HORDES.md › Load test); the owner accepted that cost with MaxTrackedUnits 500 by default (design §9 D65). Library lookups are a dictionary read at a wave's decision.
