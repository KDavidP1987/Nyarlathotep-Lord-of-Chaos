4. Business rules & invariants

What the plan says under “Business rules”

  1. **Twins are the human command (4.1, D3, D4):** same arguments, same validation, same Gateway.Run row, same service call, same push; only the reply differs. There is no path a twin has that the human command lacks.
  2. **One line per twin (4.2, D3, D12):** every twin answers exactly one `[NYAR:ok]` or `[NYAR:err]` line, success or failure, thrown or not; a refusal changes nothing on the server except what a file now holds after a failed save (event-library D19) and the events a pillar `off` ends (D5); `code=io reason=internal` is not such a refusal: the op threw, possibly after it changed state, so the action may be partly or fully applied and the client re-reads state (A16, D12); two or more surplus words are VCF's (D3).
  3. **Codes (4.1, D2):**
  4. **Idempotency (4.2, D5):** enable, disable, pillar: changed=0 on the held state, no write, no push. start/stop: the engine's one-instance rule.
  5. **Time (4.3, D5, D6):** confirms within 30 s of the same admin's ask (the existing armings); the rate window is 1 s, sliding; both in memory, both cleared on restart; `secs` is whole seconds rounded up.
  6. **Precedence (4.4):** the full order is VCF adminOnly > the ready guard ("still loading") > the rate gate (D6) > the argument checks > the admin log line > ActionGateway > Precedence.StartBlocker's controls (purge cooldown > General.Enabled > pillar > MaxConcurrentEvents > the definition, unchanged) (D3). There is no exception path: the twins run as Actor.Admin, as the human commands do.
  7. **"Every" sets (4.5):** - "Every admin action" is the §5 admin rows that mutate: event start, stop, enable, disable, set, reload, new, copy, delete; template use; pillar; purge. `spawn`, `announce`, `zone` and `stats reset` get no twin in this child: spawn and announce are test and chat tools with no panel state, and zone and stats belong to later children (Out of scope). - "Every path an admin mutation takes" (D1) is AdminFlows' flows, the IAdminOps members and the Logic paths D1 lists; the HumanReplies check counts the reply literals of those paths at v0.5.1 and fails a capture with fewer rows; the OutcomeReturns check covers Services/AdminOps.cs and IAdminOps. - "Every control" is every D-item of this plan whose evidence carries a `(fails when:` clause; ControlCaseTests reads this plan from the test Resources and fails when one lacks its ControlCases row (D11). - "Every path this child writes" is computed by `-Paths -DeclaredOf raphael-api-admin` (D14; known exclusion: a path created and deleted inside one step, S-7).

D3 Event twins

Logic/AdminFlows.cs holds one flow per admin verb, called by both `.nyar event <verb>` and `.nyar api event <verb> …` (Commands/ApiAdminCommands.cs, a shim that passes the context's admin id, name, position reader and IAdminOps); each flow runs, in order: the rate gate (twins only, D6), the argument checks, the admin log callback (the twin's line prefixed "api "; the purge ask logs nothing, as `.nyar purge` does in 0.5.1, and the confirm logs as today), ActionGateway.Run<T> with the verb's ActionKind from the single table AdminFlows.Kinds (so a twin and its human command cannot differ), the IAdminOps call, then the Outcome; the twin maps it to exactly one line: `[NYAR:ok] cmd=event verb=<verb> id=<id>` plus the verb's keys of contract §5a (moved from §10.1 by D10; changed, field, value, count, pillar, from, confirm, done), or `[NYAR:err] cmd=event verb=<verb> code=<code> [secs=] [arg=] [reason=]`; verbs are start, stop, enable, disable, set (with `location here`), reload, new, copy and delete [confirm]; any other verb, list and info included, answers `code=badarg arg=verb`; a missing or malformed argument answers `code=badarg arg=<id|field|value|pillar|newId|confirm>`; each twin declares one trailing optional parameter `extra`, and a surplus word answers `code=badarg arg=extra` (two or more surplus words reach VCF's own arity line, which contract §5a states)
