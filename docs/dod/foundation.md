## Purpose & typical use
- **Who:** the server admin who installs Nyarlathotep, and every later child of the Epic. The admin would say: "Give me a safe engine I can switch on, test with one command, and switch off with one command." The later children would say: "Give me events, triggers, a spawner and messages I can build a pillar on."
- **Job:** a working, tested event engine with nothing enabled by default. After this child an admin can define an event in events.json, have a schedule, the in-game night, a V Blood kill or a command start it, watch core waves spawn and despawn, read status, and purge everything; players see banners and warnings when the admin turns them on.
- **Coexists with:** the v0.1.0 scaffold (Plugin, Core, Settings, EntityExtensions), which it extends; the sibling mods on the same server; Raphael, which gets the api handshake.

## Use cases
### Typical
The admin turns on Pillars.EventSpawns, edits the seeded "spawns-example" event to enabled with a Schedule of Saturday 20:00, and runs `.nyar event reload`. At 20:00 the scheduler starts it: warnings at 60 and 10 s (if WaveWarnings is on), three waves of bandits around the configured point, a start banner, and after durationSeconds the remaining units drain away through the despawn budget and an end banner shows.
### Minimal stretch
Installed with defaults: pillars off, every seeded event disabled, all five announcement switches off. The only effects are the `.nyar` commands, the seeded events.json, state.json, and one health line every 10 minutes (D28). An admin runs `.nyar spawn CHAR_Bandit_Thug 1` once: the unit expires at its lifetime and nothing remains in state.json (D27).
### Maximal stretch
MaxConcurrentEvents events at the ceiling (10), MaxTrackedUnits at the ceiling (500), 200 definitions, a restart mid-event, 40 players online. Caps clamp and log (D22), spawns and despawns are staged per tick (D16), the boot sweep clears survivors (D21), and the tick stays within budget (D24). An admin who raises a cap past its ceiling is clamped at load (D5).

## Business rules
Restated from the Epic (the Epic is authoritative for the numbers of rule 9; Config/Settings.cs is authoritative for defaults, per Epic rule 10):
1. **Precedence** (Epic rule 1): purge > General.Enabled=false > the pillar switch > Limits caps > the definition's own values (D3). A cap clamps silently for players and loudly in the log (D22). There are no exceptions: no command, trigger or definition field can exceed a cap, and only the operator changes a cap, within its ceiling, by editing the cfg (D5).
2. **Durations are hard** (Epic rule 3): a unit's LifeTime is min(unitLifetimeSeconds when set, event end + GraceSeconds − now), GraceSeconds default 30; the event end always wins, and everything an event created is queued for despawn at its end (D3, D16, D20). A `.nyar spawn` unit belongs to no event; its lifetime is Limits.ManualSpawnLifetimeSeconds (default 300, range 30–3600).
3. **Duplicate actions** (Epic rule 8): the replies and the 5 s trigger dedupe of D6.
4. **Hard ceilings in code** (Epic rule 9): MaxTrackedUnits ≤ 500, MaxUnitsPerWave ≤ 50, MaxConcurrentEvents ≤ 10, MaxDespawnsPerTick ≤ 20; this child adds MaxSpawnsPerTick (default 10, ceiling 20; S-7). Values above a ceiling are clamped and logged at load (D5).
5. **Time** (Epic rule 6): real-clock schedules use the server-local wall clock at minute resolution and fire at most once per occurrence, keyed by local date + configured HH:mm and stored per event in state.json, so a DST-repeated minute fires once and a skipped one never; GameTime triggers fire on the day/night edge (D4).
6. **Activation** (Epic rule 13): a switched-off kind activates nothing and logs nothing per occurrence; wave warnings fire only for a wave of an active event (D13, D30).
7. **Every X** sets:
   - "every spawned unit" is SpawnLedger's registry, the only source of truth; after a restart the marker sweep (an IncludeDisabled | IncludeSpawnTag query on Buff + SpellLevel with the unit magic value, spikes S2) finds survivors (D16, D21).
   - "every mutating operation" is every ActionKind; the gateway check walks every .cs file under Commands/, Patches/ and Services/ that git sees, tracked or untracked-not-ignored (D11).
   - "every command" is the Epic's walk of every [Command] attribute in any .cs file git sees (D17, D19).
   - "every patch" is every [HarmonyPrefix]/[HarmonyPostfix] method in Patches/*.cs (D17).
   - "every template" is Resources/events.default.json plus the loaded events.json plus the built-in message pools (D15).
   A file created by this build is seen because every check runs in the post-audit on the built tree. The file walks are self-tested with a planted member outside the expected directory: commands, structural edits, file writes and patch guards by the Epic's existing fixtures, gateway-only, fault injection and the admin list by D18. The template set is exactly three enumerated sources — Resources/events.default.json, the loaded events.json and the Logic/Messages pools — and D15 fails if a source yields no template; the marker set is exactly the registered values in Logic/Markers (this child registers one, the unit marker) and D21 exercises it in game. Completeness is claimed only over those enumerated sources and registered values.
8. **One instance per definition:** a definition has at most one active instance; `event start` on an active one replies "already active" (D6).
9. **Stale-file refusal:** `event set`, `enable` and `disable` write events.json only if its write time equals the one at the last load; otherwise they refuse (D6).

### States
Event instance: Scheduled → Active → Ending (despawn queue draining) → Ended; Cancelled on purge, fault limit (D25) or boot (D21). First run: seeds events.json (D28). Empty: `.nyar status` "No active events." (D28). Loading: before Core.IsReady every command replies "still loading" and the scheduler does not tick (D28). Error: an invalid event is Disabled(reason) (D23); a faulting event is Cancelled (D25); an unavailable hook degrades its pillar (D31).
Concurrency: Harmony hooks, chat commands and the scheduler coroutine all run on the server main thread, so every mutation is serialised in arrival order with no locks (Epic Design › States). The races that remain are sequences, not threads, and each is a D6 or D16 case: two admins starting one event, a reload during a running event (running instances keep their snapshot), a spawn or purge during a drain, two requests for the last free slot, a trigger repeated within 5 s. The operator editing events.json by hand while an admin runs `event set` is caught by the stale-file refusal (Business rules 9). Deploying while the server runs is a procedural matter, not a control of this plan: CLAUDE.md › Build says to stop the server first, and a locked DLL makes the copy step fail loudly.
Startup and shutdown: Core.TryInitialize (after GameDataInitializedPatch) constructs, in order, Persistence → EventStore (load or seed) → SpawnTracker (boot marker sweep queued) → TriggerBus (hooks registered through IHookRegistry) → EventRuntime (instances from state.json cancelled) → Announcer → HealthMonitor → EventScheduler (StartCoroutine, 1 s tick: spawn queue, despawn queue, triggers, event ticks, announcer queue, state flush), then sets IsReady. Plugin.Unload stops the coroutine, flushes state.json once, unpatches Harmony and unregisters the VCF commands. The DeathEvent and UserConnect patches call into TriggerBus and Announcer only when Core.IsReady.
Restart: every event is cancelled on boot and marked survivors are queued for despawn (Epic S-11, D21). A correction to a definition applies to the next start, never to a running instance (D6).
### Permissions
Actors, per Epic Design › Permissions: (a) server admin in game, (b) the operator editing files on disk (fully trusted), (c) players, (d) the game and other mods (triggers only), (e) builders (Claude builds; Codex read-only), (f) the Raphael client acting as its own player. Every mutating operation is an ActionKind through Logic/ActionGateway (D10, D11): Admin gets every ActionKind of this child; Operator gets LoadDefinitions; System (the scheduler and TriggerBus) gets StartEvent and EndEvent for enabled definitions only; Player gets none in this child. Players may run only `.nyar`, `.nyar status` and `.nyar api version`, where VCF (the chat-command library, see Interfaces) refuses everything else with its standard reply; for example a player typing `.nyar event start x` gets the library's "no permission" line and nothing runs (D26). A gateway denial logs "gateway: denied <kind> for <actor>" (D10). Any admin may stop or change any event, whoever started it; an event started by System can be stopped by an admin, and a purge ends events of every origin.

## Security
- Authorization: VCF admin-only on every mutating command (D17, D26), and behind it the gateway table (D10) with the gateway-only check (D11), so an indirect path (a schedule, a trigger, a hook) can only start or end an enabled definition as System and can never reach a command. Debug.FaultInjection is a cfg key that exists only in Debug builds (D17 "fault injection: debug-only", D25).
- Injection: `.nyar announce` text and names are limited and stripped per D14. Templates substitute only {faction}, {minutes}, {event}, {zone}, {wave}, {waves} (D15, D5). Files use constant names only (D7). No input reaches a shell, a URL or a query.
- Secrets: the mod has none; the release uses gh's own credential store and TCLI_AUTH_TOKEN only in the publishing shell (Epic Security). D17 includes the secrets scan.
- Personal data: admin names and SteamIDs appear in the log for mutating commands ("admin <name> (<steamid>) ran <command>"), which BepInEx overwrites on each boot; audit records never quote a SteamID. `.nyar debug here` and state.json hold positions and are admin-only or on disk; player replies and announcements never carry positions (D15).

## Performance
Budget: scheduler tick under 1 ms idle, under 5 ms at 150 tracked units, under 15 ms at 500 (D24). The hot paths are the despawn queue (MaxDespawnsPerTick, default 5, ceiling 20; Beelzebub's 36-destroys-in-one-frame crash, DEV_REMINDERS #8), the spawn queue (MaxSpawnsPerTick, default 10, ceiling 20; S-7) and the death-event read, which touches only the frame's DeathEvents. | Bound | Why this number | At the bound | Valid case excluded, and the way to reach it |
|---|---|---|---|
| MaxTrackedUnits 150, ceiling 500 | Epic rule 9; 500 is the largest count D24 measures under 15 ms | spawn skipped, "skipped by MaxTrackedUnits" (D22) | a 300-unit spectacle: raise the cap to ≤ 500 |
| MaxUnitsPerWave 20, ceiling 50 | Epic rule 9; one wave is spawned over several ticks at MaxSpawnsPerTick | wave clamped, "clamped by MaxUnitsPerWave" (D22) | a 50-unit wave: raise the cap |
| MaxConcurrentEvents 3, ceiling 10 | Epic rule 9 | start refused, "skipped by MaxConcurrentEvents" (D22) | overlapping schedules: raise the cap |
| MaxDespawnsPerTick 5, ceiling 20 | Beelzebub's crash on 36 destroys in one frame (DEV_REMINDERS #8); spikes drained 25 units at 5 per batch cleanly | the queue waits for the next tick (D16) | faster cleanup: raise to ≤ 20 |
| MaxSpawnsPerTick 10, ceiling 20 | spikes spawned 30 units in one frame without a fault; 10 spreads a large wave over a few seconds (S-7) | the queue waits for the next tick (D16) | a wave appearing at once: raise to ≤ 20 |
| 200 definitions, 1 MB events.json | load and validation stay well under one tick; a hand-edited file is far smaller | the file is rejected with the reason (D5) | a generated catalogue larger than that: out of scope |
| announcement queue 20, one line per second | chat readability; a burst of warnings from 10 events fits | the oldest informational line is dropped and logged (D13) | none: messages are advisory |
| `event list` 10 per page | one chat screen | "page must be 1-<n>" | none: every page is reachable |

The other ranges in Design › Data and Design › UX (id and name lengths, durationSeconds, schedule counts, conditions, spawn level and multipliers, radii, the 30 s purge window, warning offsets, share limits, the 200-character announcement) are validation limits, not scale limits: each keeps an input within what the game and the chat can show, costs nothing at run time, and is rejected with its rule (D5, D14). Their provenance is the game (levels to 120, chat lines of 480 bytes, placement radius 30 from spikes S2), the Epic's rules (durations, warning offsets, share limits) or readability (names, pages). A valid value outside one is a request for a wider range, handled by amendment.

## Rollout
### Shipping
One release, 0.2.0, at close (Epic S-19). Everything ships off: pillar switches false, every seeded event disabled, all five announcement switches false (D17). Who can turn it off: any admin with `.nyar purge confirm` (D20) and the pillar switches; the operator by deleting the DLL.
### Compatibility
From 0.1.0: the plugin GUID and every existing cfg key stay, except General.AnnounceEvents, which is retired in favour of Announcements.EventBanners (default false, Epic D41); BepInEx keeps the old line as an orphan and both changelogs say so (D37). events.json and state.json start at SchemaVersion 1; a newer version loads read-only (D8). The chat reply formats introduced here are the ones later children keep; the `[NYAR:version]` line follows the contract (D12, D32).
### Rollback
Undo in the repository: `git revert <pre-child>..<v0.2.0>` (D38 drills the range up to the drill base). On a server: install the v0.1.0 DLL from its GitHub release; v0.1.0 never reads events.json or state.json, so the files stay harmless on disk, and units already spawned expire through LifeTime and DestroyWhenDisabled (D27) or are removed by `.nyar purge confirm` before the downgrade. Nothing is written that v0.1.0 cannot live with.
### Paths walked
Walking the Build plan: step 1 writes Nyarlathotep/Nyarlathotep.sln, Nyarlathotep/Nyarlathotep.Tests/** (bin/ and obj/ ignored), Nyarlathotep/Nyarlathotep/Logic/**, docs/features/FOUNDATION.md, tools/paths-manifest.txt, .gitignore; step 2 Services/Persistence.cs, Services/EventStore.cs, Resources/events.default.json, Nyarlathotep.csproj (embedded resource), and on the server BepInEx/config/Nyarlathotep/events.json, state.json (+ .bak, .tmp, .corrupt), save-data-nyardev/** and logs/NyarDev.log (A1); step 3 Logic/**, tools/preflight.ps1, tools/preflight-checks.json, tools/preflight-fixtures/GatewayOnly/**, FaultInjection/**, AdminList/**, SessionLogs/**, LogCheck/**; step 2 also writes the -ServerWrites snapshot in the session scratchpad (outside the repository, deleted at close); step 4 Services/SpawnTracker.cs, Services/UnitSetup.cs, Patches/DeathEventPatch.cs, Commands/SpawnCommands.cs, PurgeCommands.cs, DebugCommands.cs; step 5 Services/TriggerBus.cs, EventScheduler.cs, EventRuntime.cs, WaveAction.cs, Commands/StatusCommands.cs, EventCommands.cs; step 6 Services/Announcer.cs, HealthMonitor.cs, Patches/UserConnectPatch.cs, Config/Settings.cs, Commands/AnnounceCommands.cs, ApiCommands.cs, docs/RAPHAEL_INTEGRATION_CONTRACT.md, and on the server kdpen.Nyarlathotep.cfg; step 8 the six release surfaces, Nyarlathotep/Nyarlathotep/dist/ and build/*.zip (ignored), the tag and the GitHub release asset; step 9 the $env:TEMP\nyar-rollback-<guid> worktree and its entry under .git/worktrees (both removed by `git worktree remove`); refs change only by step 8's tag.
