# DoD: Replacements — units of ours that die without a fight are replaced, under a per-run budget

**Size:** L. A schema change (a new optional `action.replacements` block in events.json) across several modules, and the first use of the fight read outside unit-watch:
- **Logic:** a new Logic/Replacements.cs (the engaged rule, the replace-or-not decision, the budget, the placement, the lines, pure behind a reader interface as Logic/UnitWatch.cs is), Model (the block on SpawnWavesAction and ApocalypseAction), Validation (the block's rules), SpawnLedger (the order's tuning, loot, hunt tag and anchor kept beside the tracked unit at Confirm), FightRead (an engaged book that does not depend on [UnitWatch] Enabled), Apocalypse (a replacement counted in the run's pending and tally), CommandArgs and DefinitionEditor (the settable fields), EventAdmin and Authoring (`event info`).
- **Patches and Services:** Patches/DeathEventPatch.cs (the engaged read before SpawnTracker.Died and the replacement queued in the same death), Patches/FightPatch.cs (its gate opens for an event with the block), Services/SpawnTracker.cs (the kept order, the replacement request), Services/ApocalypseAction.cs (the run's count), Services/HealthMonitor.cs (one entry).
- **Tools:** tools/vrclient/NyarDevTools (a dev-only `.devperish` that kills a unit with no player behind the death, never shipped), tools/vrclient/scenarios/replacements*.vrs, tools/rollback-drill.ps1 (one selftest pair), tools/preflight-checks.json, tools/paths-manifest.txt, tools/data-inventory.json.
No new external dependency, no new cfg key, no state.json change.
**Planned:** by a drafting subagent for the orchestrating session on 2026-10-14, from design §9 D53 and the owner's settled answers in D58 (2026-10-14, the recommended options; recorded below as validated assumptions), the 1.0 order of D55 (scaling first, then replacements), the Epic's A40 and the recon below. Sub-decisions D58 does not settle are labelled `reversible` with a recommendation and a fallback. Replacements is a 1.0 child, not a Halloween one, so the Epic's standard procedure applies (Rollout › Procedure of docs/dod/nyarlathotep.md; design §9 D26): a fresh-context subagent reviews the plan for up to 3 rounds, every Build plan step has a pre-audit and a post-audit with a fresh read-only Codex cross-inspection of its diff, and vrclient scenarios are the in-game evidence (CLAUDE.md › In-game tests); rubric 3, so the builder never passes a manual item.
**Request:** design §9 D58 (owner, 2026-10-14): "Opt-in per event (off unless an admin adds a `replacements` block with a budget of 0-100 replacements per event run), for every SpawnWaves form (waves, growth, swarm, hunting grounds, revenge, final-wave bosses) and apocalypse hordes and bosses; apocalypse roamers keep their own refill. A unit is engaged once it has hit a player or a player has hit it; an engaged unit's death is final. A unit of ours that dies unengaged (sunlight, water, a fall, other NPCs) is replaced at its group's spawn point, walk-checked, with its own level and stats, while budget remains; stuck-unit removals and despawns are never replaced." D53 (owner, 2026-10-13): "After Halloween (1.0): a unit that dies before it has hit a player is replaced in its set, under a per-event replacement budget; once it has hit a player it counts as engaged. Border play is left to the players' honour."

**North Star:** a server admin can let a wave or apocalypse event replace the units it loses to sunlight, water, falls or other NPCs before any player fought them, up to a budget per run, so a wave keeps its strength for the players, inside the caps and the tick budget, off unless the admin adds it, released as 0.15.0; finished when D1-D29 have evidence.

## Purpose & typical use
A server admin runs wave events, hunting grounds, revenge, swarms and the zombie apocalypse. Spawned units die to things that are not the players: sunlight on a day event, a lake beside the spawn point, a fall from a ledge, a native pack or another event's units. Each such death shrinks a wave the players never met, and an event tuned for a group arrives half empty. The admin would say: "if my units die before they reach anyone, send new ones, but not forever."

Today nothing replaces a unit (recon: SpawnTracker.Died forgets a tracked unit and only apocalypse roamers refill, by RoamerPlan.TopUp and the spread per kill, Logic/Apocalypse.cs); the only fight signal is unit-watch's fight read (Patches/FightPatch.cs, Logic/FightRead.cs), which runs only while [UnitWatch] Enabled and is wiped at death (Logic/UnitWatch.cs:478-491; docs/features/UNIT_WATCH.md:53 names this child as its next reader). The job: an opt-in block with a budget (D1, D14), an engaged read that works with or without unit-watch (D2), a replacement at the group's spawn point with the unit's own tuning (D3, D5) that holds its wave (D4), never for removals, despawns, roamers or engaged deaths (D6), inside the budget, the caps and the kill switch (D7, D8), seen in `event info` and the log (D10, D15). It extends every SpawnWaves form and apocalypse hordes and bosses and coexists with unit-watch, scaling and the scoreboard, which stay unchanged (D9, D18).

## Use cases
### Typical
The admin adds `"replacements": { "budget": 10 }` to a waveList event of 6 bandits a wave set at noon beside a river. Two bandits wander into the sun and burn before the players arrive: each is replaced at the wave's spawn point at its own level (D3), the log reads "replacement … replaced (1/10)" and "(2/10)" (D10). A player hits a third, which then flees into the sun and dies: it was engaged, so it stays dead (D2). Wave 2 waits until wave 1's last unit is really gone (D4). The admin reads "replacements now: 2/10, refused 0" in `.nyar event info` (D15).

### Minimal stretch
- No block: the event runs exactly as in 0.14.0 (D1, D18).
- Budget 0: the block is kept, nothing is replaced (D1, D6).
- Every death engaged: nothing is replaced, no line beyond the verbose engaged lines (D2, D10).
- Used once: the admin removes the block with `.nyar event set <id> action.replacements none` (D14); nothing is kept in memory past the event's end or written to state.json (D11, D15).

### Maximal stretch
- Volume: 150 tracked units dying to sunlight in one tick under budget 100: at most 100 replacements a run, each a one-unit request in the death's handling, drained within MaxSpawnsPerTick, cut by the free MaxTrackedUnits slots with the refusals counted (D7, D10); the fight read's cost is the 0.083 ms a call unit-watch's spike measured, now also running for events with the block (D22).
- Abuse: a player lures units into the sun to farm them: the budget bounds it, and border play is left to the players' honour (design §9 D53, Out of scope); a player who hits a unit once makes its death final, as intended (D2); a player cannot reach the fields: they are admin-only (D14, D16).
- Repeated or parallel use: two events with the block each spend their own budget and share the caps (D7); `event set` the same value twice stores it once (D14); a replacement that dies unengaged spends again, so the budget, not the unit, is the bound (D7).

## Business rules
1. **Opt-in** (D1, D14, S-13): replacements act only for a definition whose action carries the block; budget 0-100 per event run.
2. **Engaged** (D2, S-4): a hit between the unit and a player in either direction, a player kill, or a player target within reach at death; held per tracked unit, read before SpawnTracker.Died.
3. **Replacement** (D3, D5, S-6, S-7): one order per unengaged death with budget left, same prefab, event and ledger wave, the original order's tuning, loot, hunt tag and anchor, at its group's spawn point, walk-checked, with the original's due time.
4. **Wave held** (D4, D5): the replacement is queued inside the death's handling, so its wave never reads cleared in between.
5. **Never** (D6): engaged deaths, removals, despawns, `.nyar spawn`, events without the block or with budget 0, apocalypse roamers, an earlier instance's units, deaths after the instance ended, failed replacement spawns.
6. **Precedence** (4.4): the kill switch, General.Enabled, the pillar switch, an instance's end and MaxConcurrentEvents beat replacements (D8); the free MaxTrackedUnits slots and the wave's queued size beat a replacement, which then spends no budget and is not retried (D7, S-9); an unknown engagement counts as engaged, never more units (D12, S-11); a player's kill credit beats a replacement (D9). The owner decides an exception, through design §9.
7. **"Every" sets** (4.5): "every SpawnWaves form" is the decision points that queue units for a SpawnWaves event: WaveAction's single-centre and fanOut waves (units form, waveList, growth-generated waves, swarm, revenge's focus-only waves, Region waves through RegionWave) and the final wave's bosses (BossWave.Units), all through SpawnTracker.RequestWave (Services/WaveAction.cs:135-136, Services/SpawnTracker.cs:153-162), each a case of D3; apocalypse queues through ApocalypseRun.Queue (Logic/Apocalypse.cs:875-886) for hordes, bosses and roamers, cases of D5 and D6; `.nyar spawn` is the queueing path left out on purpose (D6). "Every way a unit leaves" is a death (DeathEventPatch, the one path D2-D5 act on), a unit-watch removal, a despawn by lifetime, stop, purge, pillar off, General.Enabled false, the game, the boot sweep or the grace cleanup (D6, D8). "Every end path" is D15's eleven, the set of EndPath (Logic/Scoreboard.cs:170) and ApocalypseEnd (Logic/Apocalypse.cs:604, Disable included).
- whole: none — a replacement is one order per death, checked exactly by D3 and D7 and logged by D10; no set of parts adds up to a reported total
- siblings: SpawnWaves waves, apocalypse hordes, apocalypse bosses, apocalypse roamers

### States
- **7.1** Empty: no block, nothing new (D1, D18); budget 0, nothing replaced (D1); first run: the budget starts at 0 used at the instance's start (D7); partial: a unit whose engaged read failed counts as engaged (D12); error: a throwing request leaves the death final (D12).
- **7.2** Concurrent use: deaths of one batch are handled one by one on the main thread, each reading its own engagement and spending the budget in order (D7); two events with the block spend their own budgets and share the caps (D7); a replacement and a wave decision in one tick each go through the ledger's reservation, the first taking the last free slot (D7, SpawnLedger Request); unit-watch removing a unit while it dies: the removal is a despawn, no death, never replaced (D6, D4); an admin's `event set` while the event runs takes effect at its next start (D14); Claude and the build tooling touch the dev server only between sessions, wrapped by the snapshot (D27).
- **7.3** Cancel and re-entry: every end path drops the instance's budget count, refusals and `event info` line (D15) and cancels waiting replacement orders as every waiting order (D8); a replacement is an ordinary tracked unit, ended by the existing end paths, the boot sweep and the grace cleanup, with no timed effect of its own (D6, D7); a restart drops every record, and a resumed apocalypse treats its budget as spent and rebuilds only what its record holds (D5, S-8); removing the block (`none`) or a pillar off reverts nothing already spawned (D14, D8).

### Permissions
- **2.1** Admins: the two `event set` replacements fields in chat and through the twin (D14, D16); `event info` as today (D15). The server operator: events.json (D1). Players: no new command; their hits and kills only mark a unit engaged, nothing of the player is kept (D2, D11). Unauthenticated users: none. The replacement path acts only on units this event spawned (D3, D6).
- **2.2** A player running `.nyar event set … action.replacements.*` or its twin gets VCF's own admin refusal (D14's AuthSuite, ApiAccessTests' rule for twins, D16); nothing changes and nothing is logged as an admin action.
- **2.3** Ownership: a definition belongs to the server; any admin may change any definition's block, whoever wrote it, and the change takes effect at the next start (D14); a replacement belongs to its original's event and wave, ends with them and credits like any of their units (D3, D9); an instance stopped and restarted is a new run with a fresh budget (D7).

### UX
- **11.1** Discovery: the README's Replacements section with the block, the fields and an example (D26); `.nyar event info` shows the replacements lines (D15); the `event set` usage names the fields and design §6 lists them (D14).
- **11.2** Feedback: `event set` replies the stored value or D1's reason (D14); the twin answers one ok or err line (D16); `event info` shows the budget and the running count (D15); `.nyar status` shows the health entry (D12); every new chat text is rendered in real chat in Session 1 before release (D20, profile probe 11.2).
- **11.3** Accessibility: plain text within 480 bytes, no colour carries meaning, numbers as numbers (D14, D15).
- **11.4** Activation: a replacement acts by itself at an unengaged death of a unit of an event with the block (D3); it must not act for an event without it (D1, D18), for a removal, a despawn, a roamer or `.nyar spawn` (D6), after an instance ends (D6, D8), or for an engaged unit (D2).
- **11.5** Design bar: waves keep their strength against the world but never refill a fight the players are in, and the budget ends replacements in good time: a qualitative bar judged by the owner with real players (D24).

## Security
- **10.1** Authorization: the replacements fields are admin-only in chat (D14 with -AuthSuite) and through the twin, which runs the human command's flow (D16); events.json is the operator's file; replacements queue units only through SpawnTracker's ledger for their own event (D3, D6, D7).
- **10.2** Injection: the budget is parsed as a bounded integer, never evaluated (D1, D14); the id is matched against the library's ids as for every `event set`.
- **10.3** Secrets: none added; the release keeps the token sentinel and the privacy grep (D28).
- **10.4** Personal data: hits and kills are read to mark a unit, never to keep the player; the engaged record holds the unit's key and a cause; the lines carry the event, the wave, the prefab and counts only (D10, D11); no player is named by this child.

What they do next: remove the block (`none`), stop the event, or use the kill switch, which always works (D8).
- **12.2** Logged: one "[nyar] replacement" line per replacement with the budget used, one line per refusal reason per streak, the verbose engaged line with its cause (D10); the failure line once per streak (D12); the tick timing (D22).

- **12.4** Failing cases: every test and cmd item names its fails-when and has a ControlCases row (D17); each new test's planted fault is run in its step and logged `note · planted`; the dry runs are in the Log. ## Performance
- **13.1** Budget: the existing tick budget, 5 ms average at the default caps (automation D21). Recon measurement: unit-watch's spike measured the fight read at 0.083 ms a call in a fight and 0.008 ms idle (docs/features/UNIT_WATCH.md:152-172), and its second uw-timing run held every window under 1 ms with 54 tracked (docs/dod/unit-watch.md Log). Replacements open that read for events with the block, add one dictionary read per death and one one-unit request per replacement; D19 measures the read with its gate open and D22 the whole.
- **13.2** Bounds: budget at most 100 a run (design §9 D58), the case being a day event losing a wave to sunlight; the free MaxTrackedUnits slots (default 150, at most 500) and the wave's queued size bound each replacement (D7); queueing within MaxSpawnsPerTick (default 10, D7); the engaged and kept-order records at most one per tracked unit (D2, D3). ## Rollout
### Shipping
One release, 0.15.0, a GitHub pre-release (S-14); the owner publishes to Thunderstore. 0.14.0 (scaling) is its starting point. Method: built on its own git branch `replacements`, created from the `scaling` branch tip once scaling's step 4 is done (it is), or from main once scaling merges; merged to main at the release.

Replacements ship **off**: no definition carries the block until an admin adds it, and every event kind still ships disabled (Epic D4). Who turns it off:
- any admin, for one event, by `.nyar event set <id> action.replacements none`, by budget 0, or by removing the block from events.json and `.nyar event reload` (D14, D1);
- any admin, for everything, with `.nyar pillar spawns off` or `.nyar purge confirm` (D8);
- the operator, by removing the DLL (Epic D12).

### Compatibility
- events.json gains one optional block and stays SchemaVersion 1; a definition without it is unchanged (D1, D18).
- state.json and the cfg are unchanged (D11).
- The wire keeps api 8; the twin `event set` carries the new fields with no new tag, key or push kind (D16, S-12).
- Unit-watch's fight read, marks and removals are unchanged whether [UnitWatch] Enabled is on or off (D18).

### Rollback
- **In the repository:** `git revert --no-edit v0.14.0..v0.15.0`, drilled by the rollback gate with -Plan (D25).
- **On the dev server during the build:** every session is wrapped by tools/dev-snapshot.ps1 (D27); NyarDevTools stays a dev-server-only plugin.
- **On a server:** install the 0.14.0 DLL. A definition with the block is then disabled with "unknown field action.replacements" (D25); the admin removes the block and reloads to run it without replacements. Nothing else is written, so this stays possible after data is written; replacement units are ordinary tracked units, despawned at the event's end or by the boot sweep.
- **Published release:** tags and releases are never deleted. A bad release is withdrawn by retitling it, and versions move forward only (Epic S-19).
- **Commit range:** v0.14.0..v0.15.0
