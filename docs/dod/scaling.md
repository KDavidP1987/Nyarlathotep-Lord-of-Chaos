# DoD: Scaling to the players — wave and horde sizes and levels follow the players in scope

**Size:** L. A schema change (a new optional `action.scaling` block in events.json) across several modules, and the first read of a player's gear level anywhere in the mod:
- **Logic:** a new Logic/Scaling.cs (the player count, the average, the count and level rules, the lines, pure behind a reader interface as Logic/UnitWatch.cs is), Model (the block on SpawnWavesAction and ApocalypseAction), Validation (the block's rules), Spawning (the scaled entries before WaveGate's roll and clamp; the scaled level in SpawnTuning), HuntingGrounds (RegionWave gets scaled entries), Apocalypse (HordeSchedule.Units, RoamerPlan.TopUp and the horde and roamer tuning), CommandArgs and DefinitionEditor (the settable fields), EventAdmin and Authoring (`event info`).
- **Services:** HuntAction's PlayerQuery (the admin flag and the gear level beside each row), WaveAction and ApocalypseAction (the count read before each decision), UnitSetup (the V Blood guard on a scaled level), HealthMonitor (one entry).
- **Tools:** tools/vrclient/NyarDevTools (a dev-only gear diagnostic, never shipped), tools/vrclient/scenarios/scaling*.vrs, tools/rollback-drill.ps1 (one selftest pair), tools/preflight-checks.json, tools/paths-manifest.txt, tools/data-inventory.json.
No new external dependency, no new cfg key, no state.json change.
**Planned:** by a drafting subagent for the orchestrating session on 2026-10-14, from design §9 D52 and the owner's settled answers in D57 (2026-10-14, all four recommendations taken; recorded below as validated assumptions), the 1.0 order of D55 (scaling first after unit-watch) and the recon below. Sub-decisions D57 does not settle are labelled `reversible` with a recommendation and a fallback. Scaling is a 1.0 child, not a Halloween one, so the Epic's standard procedure applies (Rollout › Procedure of docs/dod/nyarlathotep.md; design §9 D26): a fresh-context subagent reviews the plan for up to 3 rounds, every Build plan step has a pre-audit and a post-audit with a fresh read-only Codex cross-inspection of its diff, and vrclient scenarios are the in-game evidence (CLAUDE.md › In-game tests); rubric 3, so the builder never passes a manual item.
**Request:** design §9 D57 (owner, 2026-10-14): "Opt-in per event (off unless an admin adds a scaling block), for every spawner (SpawnWaves incl. hunting-grounds, revenge and swarm growth; apocalypse hordes and roamers). Players counted: living online players inside the event's action scope (every online player for a Global event), admins counted as the scoreboard's IncludeAdmins switch says, re-read before each wave or horde. Counts: each entry gets an admin-set number of extra units per player beyond the first, always clamped by MaxUnitsPerWave and MaxTrackedUnits. Level: the players' average gear level plus an admin offset, per-wave growth on top, clamped 1-120; V Blood bosses keep their own level unless the admin sets one." D52 (owner, 2026-10-13): "After Halloween (1.0): unit counts and levels scaled to the number of players in the scope and their average level; for Halloween, admins set the start level, HP and damage and per-wave growth."

**North Star:** a server admin can let any wave or apocalypse event grow with the players it is meant for, with more units per extra player and levels near their gear, inside the caps and the tick budget, off unless the admin adds it, released as 0.14.0; finished when D1-D27 have evidence.

## Purpose & typical use
A server admin runs wave events, hunting grounds, revenge, swarms and the zombie apocalypse for groups of very different size and gear. Today every count and level is fixed in events.json (design §9 D52: for Halloween the admin sets the start level, HP, damage and per-wave growth by hand), so an event tuned for four level-80 players swamps one level-40 player and bores a full group. The admin would say: "make this wave bigger when more of them show up, and make it their level."

Nothing reads a player's level today (recon: no Equipment read anywhere under Nyarlathotep/Nyarlathotep/; the closest uses are KindredCommands Services/RegionService.cs:233 and Bloodcraft Utilities/Classes.cs:1017, learned from, never pasted), and counts change only by growth (Logic/Growth.cs) and fanOut's one group per player (Logic/Spawning.cs WaveGate.DecideGroupEntries). The job: an opt-in block (D1, D14), a fresh count of the players in scope before each decision (D2), more units per extra player inside the caps (D3, D4, D5, D9) and levels from their gear (D6, D7, D8), seen in `event info` and the log (D10, D15). It extends every spawner and coexists with the Halloween knobs, which stay unchanged (D18).

## Use cases
### Typical
The admin adds `"scaling": { "unitsPerPlayer": 2, "levelFromPlayers": true, "levelOffset": 2, "levelPerWave": 1 }` to a waveList event of 4 bandits a wave. Three players of gear 38, 41 and 44 stand in the event's region; an admin among them is not counted (IncludeAdmins false). Wave 1 rolls 4 + 2 × 2 = 8 bandits per entry before the caps (D3) at level 41 + 2 = 43 (D6, D7); one player logs off before wave 2, which rolls 6 at level 41 + 2 + 1 = 44 from the two who remain (D2, D7). The V Blood boss of the final wave keeps its own level (D8). The admin reads "scaling now: 2 players, gear 41, level 44" in `.nyar event info` (D15) and one "[nyar] scaling" line per wave in the log (D10).

### Minimal stretch
- No block: the event runs exactly as in 0.13.0 (D1, D18).
- One player counted: no extra units; with levelFromPlayers the level is that player's gear plus the offset (D3, D7).
- No player counted (an admin alone with IncludeAdmins false): base counts and the configured levels (D3, D7).
- A block with levelFromPlayers false and unitsPerPlayer 1: counts only (D1, D3).
- Used once: the admin removes the block with `.nyar event set <id> action.scaling none` (D14); nothing is kept in memory past the event's end or written to state.json (D11, D15).

### Maximal stretch
- Volume: 40 online players and unitsPerPlayer 5 ask for 195 extra copies per entry; MaxUnitsPerWave (at most 50) and the free MaxTrackedUnits slots (at most 500) cut every decision, with their cap lines (D9); the player read is the one PlayerQuery already does each 5 s for Hunt (Services/HuntAction.cs), once per decision (D22).
- Abuse: a gearless alt standing in the scope lowers the average (S-17; border play is left to the players' honour, design §9 D53); a player who leaves the scope before a wave shrinks it, as intended (D2); a player cannot reach the fields: they are admin-only (D14, D16); a level can never leave 1-120 (D7).
- Repeated or parallel use: two scaled events count the same players each for themselves and share the caps (D2, D9); `event set` the same value twice stores it once (D14); an apocalypse resumed after a restart never rebuilds more units than its record holds (D5).

## Business rules
1. **Opt-in** (D1, D14): scaling acts only on a definition whose action carries the block; its keys are unitsPerPlayer 0-5, levelFromPlayers, levelOffset -20..20 and levelPerWave 0-5 (S-3, S-4, S-5).
2. **Counted players** (D2, S-9): online, alive, at a usable position, inside the action scope (all of them for Global); admins only with [Scoreboard] IncludeAdmins true; read before each wave, fanOut group, horde and top-up.
3. **Counts** (D3, D4, D5, S-8, S-10, S-11): count + u × max(0, n − 1) per entry before the chance roll; a fanOut group counts the players within minSpacing of its own player; a horde adds u × max(0, n − 1) regular units; a top-up raises perHotspot and max; bosses never multiplied.
4. **Level** (D6, D7, S-6, S-7): A = the mean of the counted players' gear levels (each rounded down), rounded half up; level = clamp(A + levelOffset + levelDelta + (w − 1) × levelPerWave, 1, 120); an absolute level stays; no average, no change.
5. **V Bloods** (D8): never take a scaled level.
6. **Precedence** (4.4): the kill switch, General.Enabled, the pillar switch and MaxConcurrentEvents beat scaling (D9); MaxUnitsPerWave and MaxTrackedUnits beat the scaled roll, cutting regular units before bosses (D9, D5); an admin's absolute level beats the scaled level, and a V Blood's own level beats both (D7, D8); a failed read falls back to the configured counts and levels, never to more units (D12). The owner decides an exception, through design §9.
7. **"Every" sets** (4.5): "every spawner" is the decision points that queue units for an event: WaveAction's single-centre and fanOut decisions (units form, waveList, growth-generated waves, revenge's focus-only waves, Region waves through RegionWave) and ApocalypseAction's horde rise and roamer top-up, each a case of D3, D4 or D5; spread roamers (Spread.Allow) and `.nyar spawn` are the queueing paths left unscaled on purpose (D5; Out of scope); "every counted player" is PlayerQuery.Read's rows filtered by D2 (PositionReader's rule for unusable positions); "every reader of the block" is Validation, the chat editor, `event info`, the twin and the two decision services (D1, D14, D15, D16); "every end path" is D15's nine.
- whole: none — a scaled count is one number per entry, checked exactly by D3-D5 and logged by D10; no set of parts adds up to a reported total beyond the existing cap lines
- siblings: SpawnWaves waves, apocalypse hordes, apocalypse roamers

Nothing new is persisted: state.json is unchanged (D11) and a restart drops every decision row. Migration (3.4): none; the block is new and optional, absent means unscaled, events.json stays SchemaVersion 1 (D1, D18).

### States
- **7.1** Empty: no block, nothing new (D1, D18); no counted player, base counts and configured levels (D3, D7); first run: the first decision reads the players (D2); partial: a player with unreadable gear counts but is left out of the average (D6); error: a failed player read runs the decision unscaled with its health entry (D12).
- **7.2** Concurrent use: two scaled events each count the players for themselves and share the caps (D2, D9); a wave decision and a roamer top-up in one tick each read their own count (D2, D5); an admin's `event set` while the event runs takes effect at its next start, as every other field does (the running instance keeps the definition it started with, D14); Claude and the build tooling touch the dev server only between sessions, wrapped by the snapshot (D26).
- **7.3** Cancel and re-entry: every end path drops the instance's decision row and its running `event info` line (D15); scaled units are ordinary tracked units, ended by the existing end paths, the boot sweep and the grace cleanup, with no timed effect of their own (D9); a restart drops every row, and a resumed apocalypse rebuilds only what its record holds (D5); removing the block (`none`) or a pillar off reverts nothing already spawned and changes only later decisions (D14, D9).

### Permissions
- **2.1** Admins: the four `event set` scaling fields and `none` in chat and through the twin (D14, D16); `event info` as today (D15). The server operator: events.json and [Scoreboard] IncludeAdmins (D1, D2). Players: no new command; their rows are read for one decision (D11). Unauthenticated users: none. The decision services act only on units this event queues (D9).
- **2.2** A player running `.nyar event set … action.scaling.*` or its twin gets VCF's own admin refusal (D14's AuthSuite, ApiAccessTests' rule for twins, D16); nothing changes and nothing is logged as an admin action.
- **2.3** Ownership: a definition belongs to the server; any admin may change any definition's block, whoever wrote it, and the change takes effect at the next start (D14, Design › States 7.2); a counted player owns nothing here; an admin who stops being one (IncludeAdmins, User.IsAdmin) is counted or not at the next decision (D2).

### UX
- **11.1** Discovery: the README's Scaling section with the block, the fields and an example (D25); `.nyar event info` shows the scaling lines (D15); the `event set` usage names the fields and design §6 lists them (D14).
- **11.2** Feedback: `event set` replies the stored value or D1's reason (D14); the twin answers one ok or err line (D16); `event info` shows the config and the latest decision (D15); `.nyar status` shows the health entry (D12); every new chat text is rendered in real chat in Session 1 before release (D20, profile probe 11.2).
- **11.3** Accessibility: plain text within 480 bytes, no colour carries meaning, numbers as numbers (D14, D15).
- **11.4** Activation: scaling acts by itself at each decision of an event that carries the block (D2, D3); it must not act on an event without it (D1, D18), on `.nyar spawn` or on spread roamers (D5), after an event ends (D15), or on a V Blood's level (D8).
- **11.5** Design bar: a group of real players meets waves that feel sized and levelled for them, a lone player is not swamped, a V Blood keeps its fight: a qualitative bar judged by the owner with the players (D23).

## Security
- **10.1** Authorization: the scaling fields and `none` are admin-only in chat (D14 with -AuthSuite) and through the twin, which runs the human command's flow (D16); events.json is the operator's file; no new read reaches a player; scaling queues units only through SpawnTracker's ledger for its own event (D9).
- **10.2** Injection: the field values are parsed as bounded integers and a bool, never evaluated (D1, D14); the id is matched against the library's ids as for every `event set`.
- **10.3** Secrets: none added; the release keeps the token sentinel and the privacy grep (D27).
- **10.4** Personal data: player rows and gear levels are read for one decision in memory, never logged, replied, pushed or saved; the lines carry counts and the average only (D10, D11); no player is named by this child.

## Failure & observability
- **12.1** What the admin sees: "scaling: player read failing" in `.nyar status` (D12); D1's reason in an `event set` reply or `event info`'s disabled line (D1, D14); the scaling lines in `event info` (D15). What they do next: remove the block (`none`), stop the event, or use the kill switch, which always works (D9).
- **12.2** Logged: one "[nyar] scaling" line per decision with the count, the average, the level and the counts before and after (D10); the failure line once per streak (D12); the cap lines as today (D9); the tick timing (D22).
- **12.3** Knowing it is broken: the health entry (D12), the dependency suite (D13), -LogCheck after every session (D26), the vrclient scenarios (D20, D21) and the owner's session with real players (D23).
- **12.4** Failing cases: every test and cmd item names its fails-when and has a ControlCases row (D17); each new test's planted fault is run in its step and logged `note · planted`; the dry runs are in the Log. Empty inputs: no counted player (base, D3), no readable gear (own level, D6, D7), a block that scales nothing (refused, D1), a -TimingSpan log with no windows (fails, D22), a -DependencySuite with no category (fails, D13). Thresholds cite their source: 0-5 units, -20..20 offset and 0-5 per wave (S-3, S-4, S-5), 1-120 (LevelArg, design §9 D57), the rounding (S-6, confirmed by D19), 5 ms (automation D21), 50 and 500 (Logic/Limits.cs).

## Performance
- **13.1** Budget: the existing tick budget, 5 ms average at the default caps (automation D21). Recon measurement: unit-watch's second uw-timing run (docs/dod/unit-watch.md Log, unit-watch-20261014-135523.json) held every window's average under 1 ms with 54 tracked, with the 5 s player scan of Hunt (PlayerQuery.Read on its persistent query; a new query per read had cost up to 295 ms, automation A6) running. Scaling adds one PlayerQuery.Read and one Equipment read per counted player per decision (a wave every interval, a horde every everyMinutes, a top-up every 60 s), cheap ECS reads; D19 measures the read and D22 the whole.
- **13.2** Bounds: MaxUnitsPerWave (default 20, at most 50) and the free MaxTrackedUnits slots (default 150, at most 500) bound every scaled decision, the case being 40 players at unitsPerPlayer 5 (D9); unitsPerPlayer at most 5 (S-3), excluding a per-player multiplier larger than the base wave; roamers at most Limits.MaxRoamers (100, D5); levels 1-120 (D7); queueing within MaxSpawnsPerTick (default 10, D9).

## Rollout
### Shipping
One release, 0.14.0, a GitHub pre-release (S-15); the owner publishes to Thunderstore. 0.13.0 (apocalypse and unit-watch) is its starting point.

Scaling ships **off**: no definition carries the block until an admin adds it, and every event kind still ships disabled (Epic D4). Who turns it off:
- any admin, for one event, by `.nyar event set <id> action.scaling none` or by removing the block from events.json and `.nyar event reload` (D14);
- any admin, for everything, with `.nyar pillar spawns off` or `.nyar purge confirm` (D9);
- the operator, by removing the DLL (Epic D12).

### Compatibility
- events.json gains one optional block and stays SchemaVersion 1; a definition without it is unchanged (D1, D18).
- state.json and the cfg are unchanged (D11).
- The wire keeps api 8; the twin `event set` carries the new fields with no new tag, key or push kind (D16, S-14); a Raphael client on api 8 can set them as any other field.

### Rollback
- **In the repository:** `git revert --no-edit v0.13.0..v0.14.0`, drilled by the rollback gate with -Plan (D24).
- **On the dev server during the build:** every session is wrapped by tools/dev-snapshot.ps1 (D26); NyarDevTools stays a dev-server-only plugin.
- **On a server:** install the 0.13.0 DLL. A definition with the block is then disabled with "unknown field action.scaling" (D24); the admin removes the block and reloads to run it unscaled. Nothing else is written, so this stays possible after data is written; units spawned by a scaled wave are ordinary tracked units, despawned at the event's end or by the boot sweep.
- **Published release:** tags and releases are never deleted. A bad release is withdrawn by retitling it, and versions move forward only (Epic S-19).
- **Commit range:** v0.13.0..v0.14.0

## Out of scope

  - Scaling `.nyar spawn` and apocalypse spread roamers: a manual spawn has its own count and level argument, and spread is tied to kills, not to the players in scope (Business rules 7).

  - Scaling HP, power or speed multipliers by the players: D57 scales counts and levels only; the admin's multipliers stay as set (D18).
  - A global cfg switch or per-server defaults for scaling: opt-in per event only (D57).
