# DoD: Wave variety — pursuit, unit and boss pools, timed and onslaught templates, wider allied groups

**Size:** L. A schema change (three optional keys, `action.pools`, `action.pursuit` and a wave's `bosses`, and a `pool` form of a unit entry, in events.json) across several modules:
- **Logic:** Model, Validation, CommandArgs, DefinitionEditor, EventAdmin, Authoring, FactionGroups, Spawning (BossWave, the wave's roll), HuntingGrounds (the hunt phase gains pursuing events), Arena (a pursuing event's arena lifts), and new Logic/Pools.cs (the roll) and Logic/Pursuit.cs (when a run goes on the offensive).
- **Services:** WaveAction (the roll at the wave's decision), HuntAction (a pursuing event's targeting), EventScheduler and SpawnTracker (the pursuit watch), HealthMonitor (one entry).
- **Resources:** templates.json (14 templates). **Tools:** tools/rollback-drill.ps1, tools/preflight-checks.json, tools/vrclient/scenarios/{faction-mix-wide,pursuit,wave-variety}.vrs.
No new external dependency, no new cfg key, no new command.
**Planned:** interactively; the owner settled the four decisions on 2026-10-16 (design §9 D61, Epic A44). The Halloween track's process applies (design §9 D34): one review round, two at most; Codex once on the child's diff before release; vrclient scenarios as the in-game evidence; the owner judges look and feel only.
**Request:** the owner, 2026-10-16: "in the event that there are no players nearby, the units begin to hunt players ... Set this up as a modifier for the event ... Not that every event should"; "additional templates ... the waves have a timer. If the waves aren't defeated in the appropriate amount of time, then the next wave comes regardless"; "a version that is more difficult ... more mobs, more units, with unit varieties, And more bosses included, not only at the end of the wave"; "designate, in association with the template, a grouping of units by type, and then have a number designated, it would select a random set within that group. Including bosses, separately"; "we also need the ability to designate that maybe it's multiple bosses at once ... one boss is, of course, simpler and probably should be tested first"; "run tests in-game ... to spawn in groups of units and see what they are and are not compatible with, as well as the bosses".

**North Star:** a server admin can make any wave event chase players who run from it, draw each wave's units and bosses at random from named pools, and start 14 new ready-made timed and onslaught events built on wider, in-game-checked allied groups, shipped in the Halloween release 0.13.0 with apocalypse; finished when D1-D24 have evidence.

## Purpose & typical use
An admin runs a wave event for players who can simply walk away from it: the units leash at their spawn and the fight waits. With pursuit (C1) the run goes on the offensive once nobody has stood in its area for a minute, and the units come for the nearest player. The admin wants variety too: a wave of "twenty from the church's foot soldiers" and "one or two of these bosses" so no two runs look alike (C2), on factions whose units are checked in game not to fight each other (C3), and fourteen ready-made events that use all of it (C4).

## Use cases
### Typical
The admin stands in a field and runs `.nyar template use silverlight-onslaught`, `.nyar event enable silverlight-onslaught` and `.nyar event start silverlight-onslaught`. Wave 1 rolls ten church units from the foot pool; every 75 s another wave comes, cleared or not. Wave 3 brings one random boss, the final wave one or two. The players fall back to regroup: 60 s after the last of them left the arena the log says "pursuit: on", and the units jump unseen toward the nearest player, arriving 50-60 m off and walking the rest. One player runs into a castle: the units go for another player or wait outside.

### Minimal stretch
- 8.1 A pool of one unit, an entry drawing 1, a roll of 1-1: exactly that unit and that boss (D2, D3, D5); pursuit on an event with one wave of one unit: it pursues until the event ends (D8).
- 8.2 Used once: the templates stay disabled, a roll lives with its wave, pursuit state with its run; nothing is written to disk (D5, D9).

### Maximal stretch
- 9.1 Volume: a wave is at most 50 units by validation, clamped to MaxUnitsPerWave (default 20) and the free MaxTrackedUnits slots (default 150) at spawn, bosses kept first (D2, D5); at most 8 pools of 30 units and 5 bosses a wave (D1, D3); pursuit spends the region phase's 20 jumps per tick shared across events (D8, D20).
- 9.2 Abuse: a player can hide in claimed territory (a refuge by design, D61) or stay in PvP combat; the units then go for another player or wait (D8). A timed run left alone piles up to the caps, then waits for free slots (D15). Rolling a run again by stop and start rerolls it, as any start does.
- 9.3 Repeated use: one instance per definition, as today; a stop and start inside the grace never moves the old instance's units (D9).

## Business rules
1. **Pools** (D1, D2, D5): named per action; a pool entry draws its count with repeats; a boss roll draws min..max distinct bosses; rolled once per wave at its decision.
2. **Bosses** (D3, D5): fixed and rolled bosses lead their wave; the action-level `bosses` stays the final wave's (D51) and a wave's own `bosses` adds bosses to any wave; never both on the last wave.
3. **Allied** (D4, D14): a template's pools follow FactionGroups like its prefabs; D60's per-wave rule applies to pools wave by wave.
4. **Pursuit** (D8, D9): opt-in; it ignores action.scope (a scoped or Region-location run chases off its scope, as D61's "anywhere on the map" says; regionLock keeps a run inside, so the two are refused together, D7); starts once no eligible player stood in the area for afterSeconds; lasts until the run ends; lifts the arena; the eligible rule is the apocalypse roamers' (RoamRule.Eligible), a Revenge run's focus alone.
5. **Precedence** (4.4): the caps beat a roll; the kill switch beats pursuit (a purge ends it, D9); validation beats chat (D10); pursuit never moves a unit it did not spawn for this instance; a claimed territory is never a landing (D8).
6. **"Every" sets** (4.5): every end path is the seven of D9; every mover of our units is the arena (lifts while pursuing), the region lock and RegionHunt (refused beside pursuit, D7), unit-watch (its landing ignores the arena and its stall backstop skips a pursuing run, D8; its other rules unchanged: a pursuer that jumps is moving), the apocalypse (no SpawnWaves action, untouched) and pursuit itself; every reader of a wave's units (counts, clear, scoreboard, event info, unit-watch, the scale plan) reads the roll, not the pools (D5); every place a template's prefabs are checked (FactionGroups.Problem, the authoring warning) reads pool members (D4).
- whole: none — a roll draws from pools but no list of parts here must add up to a total
- siblings: spiders, undead, militia, Church of Light, Legion, Gloomrot, cursed

### States
- **7.1** Empty: a pool entry of count 1 from a one-unit pool spawns that unit; a run whose players never leave never pursues; an error is a refused definition with its reason (D1-D3, D7) or the pursuit check's health entry (D12).
- **7.2** Concurrent use: two pursuing runs share the tick's 20 jumps (D8, D20) and each moves only its own units; two admins editing one definition race through the event library's single writer, as today; an edit while a run runs applies at its next start (the running instance keeps its definition, wave-sets D13).
- **7.3** Cancel and re-entry: every end path drops pursuit (D9); a stop mid-roll stops the queued units as today; a restart starts nothing pursuing (D9); a stop and start rerolls.

### Permissions
- **2.1** Admins: `event set` the new fields (admin-only, D10), start and stop. Players: no new command; they are pursued and counted on the scoreboard. The operator: no new cfg key. Unauthenticated users: none.
- **2.2** A player running `.nyar event set` gets the existing admin-only refusal; nothing is logged as an admin action (D10).
- **2.3** Ownership: a definition belongs to the server; a running instance keeps its definition when another admin edits it (7.2).

### UX
- **11.1** Discovery: `.nyar template list` lists the 14 templates (D15, D16); `event info` shows pools, entries, rolls and pursuit (D6); the READMEs (D22).
- **11.2** Feedback: refusals name the field (D1-D3, D7, D10); the roll and pursuit lines go to the log, and the existing wave and start lines to chat, rendered in real chat in the sessions (D17, D18).
- **11.3** Accessibility: plain text within 480 bytes (D6); no colour carries meaning.
- **11.4** Activation: pursuit acts only for an event with the key while it runs, and only after afterSeconds with no eligible player in its area (D8); a roll only for a wave with a pool entry or a boss roll (D5).
- **11.5** Design bar: the pursuit reads as a threat and the rolls give varied waves; a qualitative bar judged by the owner (D19).

## Security
- **10.1** Authorization: every new field goes through `.nyar event set` and its admin-only api twin `.nyar api event set` (D10, D11); no new command, wire command or cfg key (D11).
- **10.2** Injection: pool names are checked against a-z, 0-9 and "-" (D1); prefabs against the catalog (D1); numbers parsed, never evaluated (D2, D3, D7); a roll cannot outgrow the caps (D2, D5).
- **10.3** Secrets: none added (D24).
- **10.4** Personal data: the pursuit lines carry no name, platform id or position (D8, D11); a player's position is read in memory for one check and never stored.

## Failure & observability
- **12.1** What the admin sees: a refused definition's reason in `.nyar event list` and the log; a roll in the log (D6); "pursuit: check failing" in `.nyar status` (D12). What they do next: fix the key, or stop the event; the kill switch always works.
- **12.2** Logged: "event <id> wave <n>/<N> rolled: …" (D6); "event <id> pursuit: on, no player within <r> m for <s> s" and "event <id> pursuit: group <g> on a player" (D8); "[nyar] pursuit <id>: check failed: <message>" once per streak (D12); the hunt phase's existing jump and wait lines.
- **12.3** Knowing it is broken: the health entry (D12), -LogCheck after every session (D23), the vrclient scenarios (D13, D17, D18).
- **12.4** Failing cases: every test and cmd item names its fails-when and has a ControlCases row (D12); each new test's planted fault is run in its step and logged; the dry runs are in the Log.
